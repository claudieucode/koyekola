# Palier 17 — audit de sécurité (2026-10-29)

Périmètre : code du dépôt (`origin/main` = `6c589dd5`, incluant les paliers 12 à 14 et les correctifs récents), serveur de test local. **Aucun test offensif contre la production ni un service externe.** Méthode : lecture statique du code par quatre revues parallèles (contenus CMS ; contacts/API/endpoints publics ; médias/fichiers/sauvegardes ; utilisateurs/rôles/modules), puis **reproduction par test automatisé de chaque faille corrigée** (le test échoue sur le code d'avant, réussit après). Les points non reproduits sont signalés comme tels : **« signalé » = relevé à la lecture, non reproduit**.

## Sécurité déjà en place (vérifié à la lecture)
Sessions régénérées à la connexion, compte relu en base à chaque requête (suspension, suppression, changement de mot de passe ferment la session), cookie HttpOnly/SameSite=Lax/Secure auto, secret de session refusé s'il est faible en production ; réinitialisation de mot de passe par jeton haché à usage unique ; permissions par rôle (`organizations.js`) relues à chaque requête ; barrière de portée par route (`routeScopes.js`, un test énumère les routes) ; accès aux contacts par site (`siteAccess`) ; clés d'API hachées SHA-256 avec portée figée ; webhooks entrants signés (HMAC, `timingSafeEqual`) ; webhooks sortants à IP épinglée ; médiathèque : type lu dans les octets, SVG/HTML refusés, `nosniff` ; contenu rendu assaini par liste blanche ; SQL paramétré (tables et `ORDER BY` par listes fermées) ; hôte inconnu → 421 ; aperçus partagés : jeton 192 bits haché, expirant.

## Vulnérabilités CONFIRMÉES et corrigées (reproduites par test)
| # | Gravité | Faille | Correction |
|---|---|---|---|
| F1 | Élevée | Un membre limité au site A pouvait ajouter à une liste de son site un contact d'un autre site (puis le lire) ; « Introuvables » servait d'oracle d'existence d'une adresse de l'organisation | `admin.js` (traité comme inexistant, même message) + `audience/lists.js` (`addToList` : `siteAccess.canRead`) |
| F2 | Élevée | `/api/mobile/login` délivrait une clé d'API « write » à un compte suspendu | `mobile-auth.js` : refus si `users.status != active` |
| F2b | Élevée | Une clé d'API continuait de fonctionner après suspension / retrait / suppression de son créateur | `api/keys.js` (`authenticate` refuse si le créateur n'est plus actif) ; `cmsAccess.removeFromTeam` et `account.deleteAccount` révoquent ses clés |
| S1 | Élevée | Composants : la route validait `site_id` du corps mais le service utilisait `global`/`siteId` : un membre limité au site A pouvait créer un composant **global** ou dans le site B, ou globaliser/déplacer le sien | `pages/index.js` `createComponent` / `updateComponent` : un accès limité reste dans SON site |
| S2 | Moyenne | Import CSV de redirections : `redirects.external` contournable (séparateur `;` dans la source) | `siteSeo.js` : refus de tout `http(s)://` sans la permission |
| U2 | Moyenne | Le journal d'activité (rôles, connexions, adresses des invités, tous les sites) n'exigeait que `tools.view` (éditeur) pour l'équipe | `auditJournal.js` : `audit.read` (administrateur) pour tous |
| U3 | Moyenne | `statut` d'un compte : un administrateur pouvait suspendre/désactiver n'importe quel compte LMS (élève, client) sans appartenance | `cmsAccess.setStatus` : seuls les comptes d'équipe ou de site de l'organisation |
| U4 | Moyenne | Suppression de compte : appartenances, clés d'API conservées ; fiche anonymisée encore « active » et comptée comme propriétaire (contournait « dernier propriétaire ») | `account.deleteAccount` : retrait des appartenances, révocation des clés, refus pour le dernier Super administrateur |
| S3/S5 | Moyenne | Cycle de vie d'un site (archiver, restaurer, dupliquer, récupérer), en-tête/pied, restauration d'une version de page, aperçu/comparaison de versions : permissions plus faibles que les chemins équivalents | `siteWeb.js` : `pages.publish` (archiver/restaurer), `appearance.parts`, dupliquer/récupérer réservés à l'équipe ; `landing.js` : `revisions.restore` / `revisions.view` |
| SSRF | Moyenne | Le vérificateur de liens SEO suivait des URL internes (127.0.0.1, 10.x, 169.254.169.254) et leurs redirections : scan interne par le serveur | `seo/audit.js` : `safeLookup` + `checkUrl` (comme l'import de flux), redirections suivies à la main (4 max) |
| CSV | Faible | Export CSV des redirections : formules (`= + - @`) non neutralisées | `seo/redirects.js` `csvCell` |
| UP | Faible | Champ `twitter_image` hors liste des champs image : aucun contrôle de type, fichier orphelin | `middlewares/upload.js` |

Effet de bord documenté : l'éditeur d'équipe n'ouvre plus le journal d'activité ; un accès limité à un site ne peut plus dupliquer/récupérer un site ; un rôle personnalisé sans `pages.publish` ne peut plus archiver un site.

## Signalés, NON corrigés dans ce palier (voir LIMITATIONS)
Écriture partielle sur révision périmée (`POST /pages/:id`), publication sans contrôle de révision, composants sans révision obligatoire, duplication de site sans remappage des composants, noms uniques par organisation (fuite d'existence), automatisation → webhook d'organisation (F3 audience), suppression d'un contact multi-sites par son site d'origine (décision D2), pièces jointes de formulaire, mémoire des téléversements (50 Mo × 20 en mémoire), import « mettre à jour » d'un brouillon d'un autre site (comptes d'équipe plafonnés), droit d'import contrôlé sur le mauvais site, SSRF aveugle du ping (rebond DNS), invitation d'un e-mail déjà inscrit non vérifié, limitation de connexion/inscription faible et énumération, activation de modules par un rôle de site, `X-Forwarded-Host`, contrôle d'origine sans en-tête (atténué par SameSite=Lax), lacunes de journalisation.
